# Comprehensive Benchmark Audit Protocol

You are the Lead Performance Auditor for the benchmarking system of the Pavis project.
Your task is to perform a strict, evidence-based audit of the benchmark setup
to determine whether the reported performance results are trustworthy,
comparable, and decision-grade.

This is an AUDIT, not a benchmark redesign or optimization proposal.

============================================================
GLOBAL RULES (NON-NEGOTIABLE)
============================================================

1. Scope:
   - Analyze ONLY the benchmark-related components explicitly listed below:
     * bench/ (orchestration scripts, cases/*.sh, config/)
     * crates/pavis-benchkit/ (INCLUDING bench-upstream and bench-loadgen binaries)
     * docs/benchmark/ (methodology and case definitions)
     * CI workflow: .github/workflows/bench.yaml
   - The custom upstream implementation (bench-upstream) is IN SCOPE
     and MUST be audited as a workload-defining component.
   - Do NOT assume behavior not directly observable from scripts, code, or documentation.

2. Evidence:
   - EVERY finding MUST cite concrete evidence:
     - file path
     - script / binary / document name
     - exact command, config key, or code snippet reference

3. No Redesigns:
   - Do NOT suggest alternative benchmark tools, upstreams, or architectures.
   - Do NOT propose performance optimizations.
   - Focus strictly on what the current benchmark actually measures and guarantees.

4. Output:
   - Generate ONLY ONE final Markdown summary report.
   - Write this output to the path specified in the FINAL SUMMARY section.
   - All intermediate phases are internal reasoning only and must NOT be emitted as standalone files.

5. Phase Isolation (CRITICAL):
   - Each phase MUST address ONLY its stated goal.
   - Do NOT comment on topics that belong to later phases.
   - Findings from ALL phases must be consolidated into the Final Summary.

6. Output Overwrite Rule (CRITICAL):
   - The final target output file (docs/audit/benchmark.audit.summary.md)
     MUST be a complete, standalone replacement.
   - Treat the file as EMPTY and generate a full replacement.
   - Do NOT merge, append, or reference any existing content.

7. Report Metadata Requirement (CRITICAL):
   - EVERY generated report MUST begin with a metadata header containing:
     - Audit phase name
     - Target module (Benchmark)
     - Generation timestamp (ISO 8601 format, UTC)
     - AI model identifier (exact model name if known; otherwise "unknown")

============================================================
BENCHMARK-SPECIFIC PRINCIPLES
============================================================

Benchmarks MUST:
- execute real proxy binaries or containers
- use real traffic generators (wrk / bench-loadgen)
- treat the custom upstream (bench-upstream) as part of the benchmark contract
- clearly distinguish open-loop vs closed-loop behavior
- ensure fair resource constraints across compared proxies
- produce results traceable to exact inputs, configs, AND upstream behavior

Benchmarks MUST NOT:
- treat a synthetic upstream as a neutral or “free” component
- rely on undocumented upstream behavior
- mix incomparable metrics across case types
- conflate orchestration success with performance success
- hide saturation, drops, or backpressure effects

============================================================
PHASE 0: Inventory & Benchmark Topology
============================================================

Goal: Establish a factual map of the benchmark system. No judgment.

Tasks:
1. Component Inventory:
   - Enumerate all benchmark-related scripts, binaries, configs, and documents.
   - Explicitly include:
     - bench-upstream binary and its configuration surface
     - bench-loadgen binary and its execution model
   - Classify components by role:
     - orchestration
     - traffic generation
     - upstream / backend
     - proxy under test
     - result aggregation

2. Execution Topology:
   - Describe how a benchmark run is executed end-to-end:
     - which processes/containers start
     - where bench-upstream runs (host vs container)
     - network layout and ports
     - control flow between bench/, benchkit, and CI

3. Entry & Exit Conditions:
   - Identify how benchmark runs:
     - start
     - determine readiness (including upstream readiness)
     - terminate and collect results

Rules:
- Do NOT evaluate correctness.
- Do NOT flag issues yet.

Output:
Internal Findings (Consolidate into Final Summary)

============================================================
PHASE 1: Workload & Upstream Semantics
============================================================

Goal: Determine what workload is ACTUALLY applied to proxies.

Tasks:
1. Case Mapping:
   - Map each case in bench/cases/*.sh to:
     - documented definition in docs/benchmark/
     - traffic model (open-loop / closed-loop)
     - target metric (throughput, latency, churn, reload, etc.)

2. Upstream Semantics (CRITICAL):
   - Analyze bench-upstream behavior as defined in code:
     - request handling model
     - response determinism
     - concurrency behavior
     - error generation (if any)
   - Identify which proxy behaviors are exercised
     and which are explicitly NOT exercised due to upstream design.

3. Parameter Transparency:
   - Identify which workload and upstream parameters are:
     - explicitly defined
     - implicitly defaulted
     - hard-coded in scripts or binaries

Rules:
- Do NOT assess fairness yet.
- Do NOT judge result quality.

Output:
Internal Findings (Consolidate into Final Summary)

============================================================
PHASE 2: Fairness & Comparability
============================================================

Goal: Assess whether proxy comparisons are meaningfully fair.

Tasks:
1. Resource Parity:
   - Verify CPU, memory, and network constraints across:
     - proxies
     - bench-upstream
     - load generator

2. Configuration Symmetry:
   - Compare proxy configurations:
     - listeners
     - routing rules
     - connection reuse
     - TLS (if present)

3. Metric Alignment:
   - Verify that metrics compared across proxies are:
     - produced under identical upstream behavior
     - not mixing open-loop and closed-loop interpretations

Rules:
- Do NOT suggest configuration changes.
- Only assess comparability based on evidence.

Output:
Internal Findings (Consolidate into Final Summary)

============================================================
PHASE 3: Measurement Integrity & Saturation Handling
============================================================

Goal: Evaluate whether the benchmark detects real performance limits.

Tasks:
1. Saturation Detection:
   - Identify how overload is detected:
     - upstream saturation
     - proxy saturation
     - load generator backpressure

2. Error Attribution:
   - Determine whether errors/drops can be attributed to:
     - proxy
     - upstream
     - load generator

3. Termination Criteria:
   - Assess whether benchmark termination reflects:
     - workload completion
     - detected saturation
     - orchestration timeout only

Rules:
- Do NOT propose new metrics.
- Focus on what is actually measured.

Output:
Internal Findings (Consolidate into Final Summary)

============================================================
PHASE 4: Determinism, Reproducibility & CI Effects
============================================================

Goal: Assess reproducibility and stability of results.

Tasks:
1. Determinism Controls:
   - Identify sources of nondeterminism in:
     - bench-upstream
     - bench-loadgen
     - orchestration scripts
     - CI environment

2. Reproducibility:
   - Determine whether a benchmark run can be reproduced locally
     using only documented commands and configs.

3. CI-Specific Behavior:
   - Analyze .github/workflows/bench.yaml for:
     - resource constraints
     - environment differences vs local runs

Rules:
- Do NOT suggest CI improvements.
- Only assess risk and evidence.

Output:
Internal Findings (Consolidate into Final Summary)

============================================================
PHASE 5: Result Interpretation & Claim Validity
============================================================

Goal: Evaluate whether the benchmark supports the claims drawn from it.

Tasks:
1. Claim Traceability:
   - Identify performance claims implied by benchmark outputs.
   - Trace each claim back to:
     - specific cases
     - specific metrics
     - specific upstream semantics

2. Overinterpretation Risk:
   - Identify where results could be misread
     due to synthetic upstream behavior.

3. Signal-to-Noise:
   - Assess whether observed differences exceed
     noise introduced by upstream or loadgen limits.

Rules:
- Do NOT challenge intent.
- Only assess evidentiary support.

Output:
Internal Findings (Consolidate into Final Summary)
