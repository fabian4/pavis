# Comprehensive Rust Crate Audit Protocol: `crates/pavis-core`

You are the Lead Code Auditor for the Rust crate `crates/pavis-core`.
Your task is to perform a strict, evidence-based, multi-phase audit
to certify its readiness for production lock-in.

This is an AUDIT, not a code review.

============================================================
GLOBAL RULES (NON-NEGOTIABLE)
============================================================

1. Scope:
   - Analyze ONLY code inside `crates/pavis-core`.
   - Do NOT assume behavior of other crates (runtime, relay, adapters).

2. Evidence:
   - EVERY finding MUST cite concrete evidence:
     - file path
     - symbol name
     - short snippet (≤15 lines)

3. No Refactors:
   - Do NOT suggest code changes, rewrites, or redesigns.
   - Focus strictly on assessing the CURRENT STATE.

4. Output:
   - Generate ONLY ONE final Markdown summary report.
   - Write this output to the path specified in the FINAL SUMMARY section.
   - Intermediate phases (0-5) are for rigorous data gathering and must be held in context or temporary reasoning, NOT written as separate permanent files.

5. Phase Isolation (CRITICAL):
   - Each phase MUST address ONLY its stated goal.
   - Do NOT comment on topics that belong to later phases.
   - Do NOT “preview” fixes or conclusions early.
   - Findings from ALL phases must be consolidated into the Final Summary.

6. Output Overwrite Rule (CRITICAL):
   - The final target output file (docs/audit/core.audit.summary.md)
     MUST be a complete, standalone replacement of any existing content.
   - Treat the file as EMPTY and generate a complete replacement.
   - Do NOT merge, append to, reference, or preserve any existing text.

7. Report Metadata Requirement (CRITICAL):
   - EVERY generated report MUST begin with a metadata header containing:
     - Audit phase name
     - Target crate (`crates/pavis-core`)
     - Generation timestamp (ISO 8601 format, UTC)
     - AI model identifier (exact model name if known; otherwise state "unknown")
   - This metadata MUST appear at the very top of the file.

============================================================
EXECUTION ORDER (MANDATORY)
============================================================

Execute ALL phases strictly in order:

Phase 0 → Phase 1 → Phase 2 → Phase 3 → Phase 4 → Phase 5 → Final Summary

You MUST conceptually complete each phase before moving to the next.

============================================================
PHASE 1: Boundary & Dependency Audit
============================================================

Goal: Enforce architectural purity.

Hard Constraints:
`pavis-core` MUST contain:
- canonical data types
- validation and invariant enforcement
- error definitions

`pavis-core` MUST NOT contain:
- filesystem / network / env I/O
- async runtimes, threads, timers
- external side effects
- runtime or deployment concepts

Tasks:
1. Code Audit:
   - Identify any I/O, async, threading, or side-effect behavior.

2. Dependency Audit:
   - Inspect Cargo.toml dependencies.
   - A dependency is a VIOLATION ONLY IF:
     it is actually used by pavis-core code
     to enable I/O, runtime behavior, or side effects.

3. Validation Audit:
   - Verify validation logic checks invariants only.
   - Example: string shape checks allowed;
     filesystem existence checks are NOT allowed.

Rules:
- This is a HARD GATE.
- Do NOT propose fixes.
- Ambiguous cases MUST be labeled “Boundary Risk”.

Output:
Internal Findings (Consolidate into Final Summary)
