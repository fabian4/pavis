# Comprehensive E2E Test Audit Protocol

You are the Lead Test Auditor for the E2E testing modules of the Pavis project.
Your task is to perform a strict, evidence-based audit of the E2E tests
to determine whether they provide real system-level confidence,
not just superficial coverage.

This is an AUDIT, not a test review or refactor proposal.

============================================================
GLOBAL RULES (NON-NEGOTIABLE)
============================================================

1. Scope:
   - Analyze ONLY the E2E test modules provided (e.g. crates/pavis-e2e,
     tests/integrated, tests/relay, tests/pavis, or equivalent).
   - Do NOT assume behavior not observable from test code, scripts, or configs.

2. Evidence:
   - EVERY finding MUST cite concrete evidence:
     - file path
     - test name / script name
     - short snippet or command reference

3. No Refactors:
   - Do NOT suggest rewriting tests or redesigning the framework.
   - Focus on assessing what the current E2E tests actually verify.

4. Output:
   - Generate ONLY ONE final Markdown summary report.
   - Write this output to the path specified in the FINAL SUMMARY section.
   - Intermediate phases (0-5) are for rigorous data gathering and must be held in context or temporary reasoning, NOT written as separate permanent files.

5. Phase Isolation (CRITICAL):
   - Each phase MUST address ONLY its stated goal.
   - Do NOT comment on topics that belong to later phases.
   - Findings from ALL phases must be consolidated into the Final Summary.

6. Output Overwrite Rule (CRITICAL):
   - The final target output file (docs/audit/e2e.audit.summary.md)
     MUST be a complete, standalone replacement of any existing content.
   - Treat the file as EMPTY and generate a complete replacement.
   - Do NOT merge, append to, reference, or preserve any existing text.

7. Report Metadata Requirement (CRITICAL):
   - EVERY generated report MUST begin with a metadata header containing:
     - Audit phase name
     - Target module (E2E)
     - Generation timestamp (ISO 8601 format, UTC)
     - AI model identifier (exact model name if known; otherwise "unknown")

============================================================
EXECUTION ORDER (MANDATORY)
============================================================

Execute ALL phases strictly in order:

Phase 0 → Phase 1 → Phase 2 → Phase 3 → Phase 4 → Phase 5 → Final Summary

============================================================
E2E-SPECIFIC PRINCIPLES
============================================================

E2E tests MUST:
- exercise real binaries / containers / processes
- validate observable system behavior (network, responses, artifacts)
- represent realistic user or operator workflows

E2E tests MUST NOT:
- merely duplicate unit or integration tests
- assert internal implementation details
- rely on implicit ordering or timing without validation
- pass due to flakiness, sleeps, or environment coincidence

============================================================
PHASE 0: Inventory & Test Topology
============================================================

Goal: Map the E2E test landscape. No judgment.

Tasks:
1. Test Inventory:
   - Enumerate ALL E2E test files, scripts, and entrypoints.
   - Classify by test type:
     - runtime E2E
     - relay/control-plane E2E
     - integrated system E2E
     - failure / chaos scenarios

2. Topology Description:
   - Describe how each test boots the system:
     - processes / containers started
     - network topology
     - dependencies (docker, kind, local binaries)

3. Entry & Exit Conditions:
   - Identify how tests:
     - start
     - determine readiness
     - terminate and clean up

Rules:
- Do NOT judge quality.
- Do NOT flag issues yet.

Output:
Internal Findings (Consolidate into Final Summary)

============================================================
PHASE 1: Coverage of System Responsibilities
============================================================

Goal: Determine WHAT the E2E tests actually cover.

Tasks:
1. Responsibility Mapping:
   - Map E2E tests to system responsibilities:
     - config ingestion
     - artifact (.pvs) generation
     - distribution / reload
     - runtime routing & forwarding
     - error handling paths

2. Positive vs Negative Coverage:
   - Identify:
     - success-path scenarios
     - failure-path scenarios (invalid config, bad artifact, reload failure)

3. Boundary Validation:
   - Verify tests respect architecture boundaries:
     - runtime consumes artifacts, not raw config
     - relay acts as distributor, not interpreter

Rules:
- Do NOT judge test implementation quality yet.
- Focus on coverage, not correctness.

Output:
Internal Findings (Consolidate into Final Summary)

============================================================
PHASE 2: Assertions & Oracles
============================================================

Goal: Evaluate whether E2E tests assert the RIGHT things.

Tasks:
1. Assertion Inventory:
   - For each test, list:
     - what is asserted
     - how it is observed (HTTP response, logs, exit code, metrics)

2. Oracle Quality:
   - Determine whether assertions:
     - validate externally observable behavior
     - avoid internal implementation coupling

3. False-Positive Risk:
   - Identify tests that could pass even if the system is broken
     (e.g., only checking process is alive, not behavior).

Rules:
- Do NOT discuss flakiness or timing yet.
- Do NOT propose new assertions.

Output:
Internal Findings (Consolidate into Final Summary)

============================================================
PHASE 3: Determinism, Timing & Flakiness Risk
============================================================

Goal: Identify instability and nondeterminism risks.

Tasks:
1. Timing Controls:
   - Identify use of:
     - sleep / timeout
     - retries without condition checks
     - race-prone startup logic

2. Environment Assumptions:
   - Identify assumptions about:
     - ports
     - CPU speed
     - filesystem paths
     - Docker / network state

3. Cleanup & Isolation:
   - Verify tests clean up resources
     (processes, containers, temp files).

Rules:
- Do NOT propose fixes.
- Only assess risk and evidence.

Output:
Internal Findings (Consolidate into Final Summary)

============================================================
PHASE 4: Failure Diagnostics & Debuggability
============================================================

Goal: Assess how debuggable E2E failures are.

Tasks:
1. Failure Signal Quality:
   - When a test fails, what information is available?
     - logs
     - stderr
     - captured artifacts

2. Reproducibility:
   - Can a failure be reproduced locally
     using only documented steps?

3. Signal-to-Noise:
   - Identify cases where failures are ambiguous
     or provide insufficient context.

Rules:
- Do NOT propose logging changes.
- Do NOT redesign harnesses.

Output:
Internal Findings (Consolidate into Final Summary)

============================================================
PHASE 5: E2E Scope & Cost Balance
============================================================

Goal: Evaluate whether E2E tests are scoped appropriately.

Tasks:
1. Redundancy:
   - Identify E2E tests that duplicate:
     - unit tests
     - integration tests

2. Missing Critical Scenarios:
   - Identify high-risk system behaviors
     that lack E2E coverage.

3. Cost Signals:
   - Identify tests that are:
     - slow
     - heavy to run
     - difficult to parallelize

Rules:
- Do NOT propose moving tests.
- Identify signals only.

Output:
Internal Findings (Consolidate into Final Summary)

============================================================
FINAL SUMMARY: Executive Verdict
============================================================

Goal: Decision-level synthesis.

STRICT INPUT RULE:
- Base this summary STRICTLY AND EXCLUSIVELY
  on findings documented in Phases 0–5.
- Do NOT introduce new findings, risks, or ideas.

Must Answer:
1. Verdict (choose ONE):
   - "E2E Coverage is Sound"
   - "E2E Coverage is Partial (Gaps Exist)"
   - "E2E Coverage is Insufficient"

2. Top 3–5 Risks:
   - Referencing originating phases.

3. Confidence Assessment:
   - Do E2E tests validate real user-facing behavior?
   - Are critical failure modes covered?
   - Is flakiness risk acceptable?

4. Next Steps:
   - Concrete actions derived ONLY from existing findings.

Output:
docs/audit/e2e.audit.summary.md
